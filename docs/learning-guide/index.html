PROJECT-BASED LEARNING

从一个 PDF 对照阅读器，学会完整的软件开发。

这不是只讲语法的教程，而是一张从“我有一个想法”走到“用户可以下载安装”的地图。你可以一边阅读，一边打开 PDF Pair 源码验证每个概念。

开始学习阅读项目说明
给初学者的建议：不要试图一次记住所有内容。先理解流程，再挑一个小功能亲手修改、测试和提交。
01

BIG PICTURE

软件开发不是“写完代码”

一个软件项目通常循环经过下面这些阶段。真实项目不会严格一次走完，而是不断迭代：发布一个小版本，收集问题，再回到需求阶段。

想法用户遇到了什么问题？
→
需求什么必须做，什么以后做？
→
设计数据、界面和模块如何协作？
→
编码把设计变成可运行的程序
→
验证测试、调试、打包和发布

本项目的实际循环

  1. 用户提出：两个 PDF 要并排阅读。
  2. 继续明确：绑定滚动、解绑、缩放、搜索。
  3. 实现最小版本：两个面板和本地 PDF 加载。
  4. 通过测试和人工试用发现问题。
  5. 生成 DEB、AppImage、MSI、NSIS 安装包。

你要养成的习惯

  • 先定义“完成”的标准。
  • 一次只改变一个主要变量。
  • 每个大更新都保存 Git。
  • 让测试替你重复检查。
  • 记录失败原因，而不是只记录成功。
02

PRODUCT THINKING

把想法变成可执行需求

“做一个 PDF 阅读器”太宽泛。好的需求要描述用户、动作和可观察结果。可以使用这个句式：

作为 用户，我希望 完成一个动作，从而 得到一个可验证的结果。
用户故事

作为论文读者，我希望同时打开新旧版本 PDF，从而快速找到内容变化。

验收标准

打开两个本地 PDF 后，窗口显示左右两个阅读区域；点击“绑定滚动”后，滚动左侧会带动右侧。

需求优先级：先做 MVP

优先级功能为什么
P0打开两个 PDF、显示页面没有它，产品没有核心价值
P0同步/独立滚动这是“对照阅读”的核心
P1缩放、搜索、页码跳转显著提高可用性
P2标注、导出差异报告有价值，但可在基础版本后加入
03

ARCHITECTURE

理解 PDF Pair 的技术分工

PDF Pair 选择 Tauri，是因为它能用 Web 技术做界面，同时用 Rust 调用本地能力。理解“谁负责什么”，比背框架 API 更重要。

React + TypeScript按钮、面板、滚动、搜索状态
IPC
Tauri + Rust文件选择、读取本地文件、桌面窗口
PDF.js解析 PDF、渲染 Canvas、提取文字
一个文件打开请求的路径
用户点击“选择 PDF”
  ↓
React 调用 fileGateway.pickPdf()
  ↓
Tauri dialog 返回本地路径
  ↓
Rust read_pdf 读取字节
  ↓
PDF.js getDocument({ data })
  ↓
React 渲染 Canvas 和文字层
边界意识：React 不应该直接知道 Rust 文件读取的细节。通过 PdfFileGateway 抽象，可以在测试里替换文件系统，也能减少模块耦合。
04

ENVIRONMENT

搭建开发环境

开发环境就是让你的电脑具备“编辑、运行、测试、打包”所需工具。版本不一致是初学者最常见的障碍之一。

1node --version检查 Node.js
2rustc --version检查 Rust
3npm ci按照 lock 文件安装依赖
4npm run tauri dev启动桌面开发模式

Ubuntu 依赖

sudo apt-get install -y \
  libwebkit2gtk-4.1-dev librsvg2-dev patchelf

如果遇到 libayatana-appindicator3 与 libappindicator3 冲突，不要盲目删除大量系统包。先记录发行版版本，再根据 Tauri 的 Linux 依赖说明选择兼容的包组合。

05

IMPLEMENTATION

从小模块开始编码

不要一开始就修改整个 App。先选一个“深度适中”的模块：输入清晰、输出清晰、依赖少，容易测试。

src/App.tsx应用状态、双面板协调
src/components/DocumentPane、PDF 页面视图
src/domain/同步滚动等纯业务逻辑
src/pdf/加载、搜索、文字差异
src/platform/桌面文件选择和 IPC
src/session/会话保存与恢复

推荐的编码顺序

  1. 先写纯函数，例如把滚动比例映射到另一个文档。
  2. 为纯函数写测试，确认边界值。
  3. 把函数接到 React 事件中。
  4. 最后再处理样式和错误状态。
深模块思维：一个好的模块用很小的接口隐藏复杂细节。例如，调用方只需要 mapScrollProgress(source, target)，不必知道锚点映射的计算过程。
06

QUALITY

测试：让程序可以放心改变

测试不是为了证明程序“永远没有 bug”，而是让你在修改后尽快知道哪些行为发生了变化。

人工/端到端真的打开桌面程序和 PDF
组件测试按钮、面板、滚动和弹窗
单元测试同步映射、文本差异等纯逻辑
红npm test先观察失败
绿npm run typecheck确认类型正确
稳npm run build确认生产构建
桌cargo test --manifest-path src-tauri/Cargo.toml确认 Rust

写一个好测试的四个部分

Arrange准备输入Act执行动作Assert检查结果Cleanup清理副作用
07

DEBUGGING

遇到 Bug 时，先建立反馈回路

调试不是猜答案，而是设计实验。每次实验只改变一个变量，并记录结果。

1. 复现明确操作步骤和错误信息
2. 缩小减少文件、页面和操作
3. 假设列出 3 个可证伪原因
4. 验证用日志或测试排除原因
5. 修复先写回归测试，再改代码
真实案例

AppImage “闪一下，然后页面无法渲染”

差分：DEB 正常，AppImage 异常。
证据：AppImage 运行在打包的 WebKitGTK 和 XWayland 后端；进程 CPU、内存异常。
修复：Wayland 环境优先原生后端；释放离屏 Canvas；文字层失败不再遮住 Canvas。
验证：加入回归测试，重新生成四个平台安装包。

08

VERSION CONTROL

Git 是项目的时间机器

Git 的核心不是“记命令”，而是保存有意义的项目快照，让你可以查看、比较和协作。

git status                         # 看发生了什么
git diff                           # 看具体改动
git add src/                       # 选择要保存的文件
git commit -m "fix: release offscreen canvases" # 保存快照
git log --oneline                  # 查看历史
git push origin master             # 同步到远程
安全规则：提交前检查 git status。不要把密码、Token、个人 PDF、构建产物和无关目录误提交。项目中的 texglot/ 就是一个应保持未跟踪、不要随意加入的例子。

提交信息的语言

feat: 新功能fix: 修复问题test: 测试docs: 文档build: 构建发布refactor: 重构

DELIVERY

从代码到用户可安装的软件

发布是一个工程流程：版本号、构建环境、安装包、校验、自动化和说明都属于产品的一部分。

版本更新 package、Cargo 和 Tauri 配置
标签git tag v0.1.1
CIUbuntu 构建 DEB/AppImage
CIWindows 构建 MSI/NSIS
发布上传资产、写更新说明

本项目的发布命令

npm run tauri:bundle
git tag -a v0.1.1 -m "PDF Pair v0.1.1"
git push origin master
git push origin v0.1.1

Ubuntu

DEB 适合已知 Ubuntu 环境，依赖系统 WebKitGTK。

AppImage 便携，但会携带更多运行库，图形栈兼容性要特别测试。

Windows

MSI 适合企业部署和标准安装流程。

NSIS EXE 适合普通用户双击安装。

10

RESPONSIBILITY

安全、隐私与长期维护

本地优先

PDF 不上传服务器，文件读取仅在本机完成。

不保存密码

密码只用于当前 PDF 加载，不写入会话。

限制输入

Rust 端检查扩展名、文件类型和最大文件大小。

依赖更新

定期查看 PDF.js、Tauri、WebKitGTK 的安全更新。

发布前检查单

  • 没有把测试 PDF、Token 或个人路径写进仓库。
  • Windows 和 Ubuntu 都完成最基本的人工试用。
  • 安装包能启动，卸载不会删除用户文件。
  • README 写明已知限制和报告问题的方法。
  • 版本号、Git 标签和 Release 资产一致。

PRACTICE ROADMAP

适合入门学生的练习路线

第 1 周读懂现有代码

找到入口、组件、测试和构建脚本；画出模块关系图。

第 2 周改一个小界面

修改按钮文字或颜色，运行测试，提交一个 docs 或 style commit。

第 3 周加一个纯函数

实现页码映射、文件名格式化或差异统计，并先写单元测试。

第 4 周加一个组件功能

实现“清除搜索”或“最近文档”，覆盖成功和失败状态。

第 5 周处理一个真实 Bug

写复现测试，记录假设，修复后重新打包。

第 6 周发布自己的版本

创建分支、提交、打标签，写 Release 说明和已知问题。

动手题

新增“每页渲染状态”

让每个 PDF 页面显示“未加载 / 加载中 / 已完成 / 失败”。要求：状态变化有测试，切换缩放不会出现旧状态，文字层失败不能让 Canvas 变成失败。

提示

从 PdfPageCanvas 的 shouldRender 和 error 状态开始，不要一上来改 App 全局状态。

GLOSSARY

入门词典

API
模块之间约定好的调用方式。
组件
可以独立组合和测试的界面单元。
IPC
前端和桌面后端之间的进程通信。
回归测试
防止已修复问题再次出现的测试。
CI
持续集成，服务器自动运行测试和构建。
Artifact
构建产生的可下载文件，例如 DEB、MSI。
Runtime
程序运行时依赖的环境和库。
MVP
最小可行产品，先验证核心价值。

YOUR NEXT STEP

不要只读完，马上做一次小改动。

打开源码，找到一个你理解的模块，写一个测试，做一个最小修改，然后用 Git 保存它。软件开发能力来自这样的完整小循环。
